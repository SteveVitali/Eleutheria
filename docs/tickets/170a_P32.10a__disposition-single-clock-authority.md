## Goal

Eliminate the flaky `tests/db/test_publication_dispositions.py` failures found by P32.10's full-suite run
(4 intermittent reds): `policy/src/policy/eligibility.py::new_disposition` stamps `decided_at` host-side
(`datetime.now(UTC)`), while the shared eligibility SQL fragments in `db/src/db/dispositions.py` filter
`d.decided_at <= clock_timestamp()` evaluated on the **container** clock. Under Docker Desktop VM clock lag a
just-recorded disposition is transiently future-dated and invisible to the selector. Make one clock — the
database's — authoritative for `decided_at`.

## In scope — deliverables

1. Server-side `decided_at` authority: add an additive sqitch change giving `disposition.decided_at` a database
   default (`now()`/`clock_timestamp()`), and stop the writer stamping host time — `new_disposition`/`record_disposition`
   accepts an explicit `decided_at` only for recorded-history/migration replay (documented), and otherwise omits the
   column so the database default applies. Existing committed `decided_at` values stay readable (append-only; no
   rewrite).
2. Regression test: a disposition recorded and immediately selected under the real PG container is visible to the
   eligibility selector — the test must fail under the old host-stamp path when the clocks differ (e.g. assert the
   insert statement does not carry a Python-`now()` value, or fake a skewed host clock).
3. If any other writer stamps `datetime.now(UTC)` into a column that SQL-side eligibility/temporal filters compare
   against the server clock, record it — fix it only if it is the same defect class in the same surface; otherwise
   open a DEFERRALS row.
