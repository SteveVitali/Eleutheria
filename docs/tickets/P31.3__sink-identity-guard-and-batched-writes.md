## Goal
Two concurrent sinks can never mint two entities for one `(scheme, value)`, and the three existing duplicate pairs
carry recorded decisions. A large land or replay becomes DB-bound instead of latency-bound, with a measured speedup
and every append-only, idempotency and resumability property unchanged.

## In scope — deliverables
1. **The identity guard.** Choose and implement one guard, recorded in **ADR-R9-SINK**: a transaction-scoped
   advisory lock per `(scheme, value)` around check-then-insert, or a new unique side table/index that excludes the
   pre-existing duplicate rows. A plain `UNIQUE (scheme, value)` cannot build over the existing duplicates, so the
   ADR must say why the chosen mechanism is sound. The guard lands as a new sqitch change if it needs schema.
   **Scope note:** `_entity_for_subject` only handles `SUBJECT_SCHEME` (`sig.connector.subject`). The `us.state OK`
   and `fr.insee 01` duplicates came from a **different writer** (the jurisdiction/org registry path). Find that
   writer and put it behind the same guard, or record why it is deliberate.
2. **Duplicate triage.** Using a read-only hosted query, list every `(scheme, value)` pair with more than one
   entity. Triage the three known pairs (`sig.connector.subject … camilo_schools_cctv:1`, `us.state OK`,
   `fr.insee 01`) with evidence (creation times, sources, what each entity carries). Record each as an append-only
   same_as or distinct resolution decision through the existing decision writer. The end state: **every** pair the
   `GROUP BY … HAVING count(DISTINCT entity_id) > 1` query returns has a recorded same_as or distinct decision.
   Append-only means both identifier rows stay, so the query still returns them.
3. **Batched writes.** Cut per-claim round trips. Cache predicates, entities, evidence and runs per chunk. Use
   multi-row `INSERT … ON CONFLICT (content_digest) DO NOTHING RETURNING` per chunk, or psycopg pipeline mode, with
   the `claim_evidence` links written in the same chunk transaction. Keep the chunked commit (P26.18) and its
   resumability.
4. **Extension points (the shared decision this ticket owns).** Expose (a) a duplicate-claim hook: the set of
   content digests that already existed in a chunk, with their `claim_id`s, which P31.7 will use; (b) an object
   resolution seam for `object_entity`, which P31.5 will use; (c) a per-capture flush entry point, which P31.4 will
   use. The behaviour stays identical until those tickets land.
5. **Measure.** On local PG18 (testcontainer), land a seeded ≥100k-claim source. Report claims/min before and
   after, and round trips per claim. Then run a **bounded hosted measurement** as a Cloud Run job next to
   `sig-pg`: a bounded replay slice of an already-landed source (+0 inserts expected, which also proves
   idempotency). Give an honest projected full-OSM-replay ETA on `db-custom-1-3840`.

**Split seam** (if the working set overflows): (1)+(2) identity guard + triage | (3)+(4)+(5) batching. The guard
lands first.

## Out of scope

- Rolling the new sink onto the scheduled OSM job (P31.4 decides that with the operator).

## Acceptance criteria
- [ ] Two concurrent sinks asserting the same new subject create exactly one entity (real-PG concurrency test) *(deterministic)*.
- [ ] Each of the 3 pairs has a recorded decision with evidence; every pair the hosted duplicate query returns has a recorded same_as/distinct decision; both entity writers are guarded (or the exception is recorded) *(live, read-only + append-only decision rows)*.
- [ ] `tests/db/test_claim_sink.py` passes unchanged: append-only, +0 replay, interrupted-resume = uninterrupted count, no UPDATE/DELETE *(deterministic)*.
- [ ] Measured claims/min and round trips per claim before/after on ≥100k claims; hosted bounded slice +0 with a projected OSM-replay ETA *(measured)*.
- [ ] ADR-R9-SINK names the guard and the three extension points (with `## Revisit trigger` + Appendix F row); `make check` + `make test-db` green.
