# P25.10 — Contradiction serve-path: bounded latency over an append-only spine (P25+ backlog)

- **Semantic id:** `API-PERF.1` · **Phase:** 25 · **Kind:** ticket · **Tag:** p25-backlog
- **base_branch:** current checkout · **Depends on:** go-public (the latency was measured live, 2026-09-16: `/v1/contradiction` → 200 in ~105 s cold)
- **Run:** `implement-spec spec=docs/tickets/P25.10__contradiction-serve-path.md live_verification=true`
- **Gate status:** engineering — no human gate.
- **Live stage:** verification should include a timing measurement against the hosted `sig-api` (before/after), recorded in the run ledger.

## Goal
`/v1/contradiction` is a defining-standard surface (§3.1: contradictions stay visible) and currently takes ~105 s cold because it is computed on every read over the whole spine. Make it fast **without ever serving a stale or incomplete contradiction set** — the fix must be as honest as the endpoint it accelerates.

## In scope — deliverables
1. **Profile first.** Establish where the ~105 s goes (SQL scan shape, per-row ORM work, N+1, in-memory pairwise pass) before choosing the fix — record the finding in the run ledger.
2. **Implement the serve-path fix.** Constraints that bound the design space:
   - **The spine is append-only.** A contradiction set computed at watermark W is exactly valid until the spine gains rows. A cache keyed on the spine watermark (e.g. `max(claim_id)` / row count — whatever the store already exposes) is *provably never stale*; prefer this over TTLs or scheduled refresh.
   - **Warm vs cold.** If per-compute cost stays heavy, compute at most once per instance — in-process memoization keyed on watermark, optionally with an async warmup after startup so even the first user request is fast.
   - **If the compute itself is the bottleneck** (e.g. an O(n²) in-memory pass over all claims), fix the algorithm or push the set-based work into SQL first — caching a fundamentally wrong-shaped query is hiding the problem.
   - **Disclose freshness.** The response should carry the watermark/as-of it was computed at (the API already models `AsOfContext`) — a cached answer states what spine state it describes.
   - A **derived/precomputed store** (new sqitch change, additive only) is an acceptable alternative if profiling shows per-instance compute is still too costly — but it must be derived data, never a hand-maintained table, and the spine stays insert-only.
3. **Prove invalidation.** A test that adds a claim creating a new contradiction and shows the endpoint reflects it (watermark bump → recompute) — the cache can never serve a silently stale set.
4. **Other read endpoints.** If the same compute-on-read pattern makes `/v1/search`, `/v1/dossier`, `/v1/coverage` slow at this spine size, apply the same watermark discipline where it's the same shape — recorded, not scope-creeped into unrelated endpoints.

## Out of scope
- Changing what a contradiction *is* or how it's computed semantically; suppressing contradictions for performance; TTL/expiry caches that can serve stale sets; writes to the spine; changes to RLS/tier filtering.
- CDN/edge caching of the API (a later infra option, not this fix).

## Acceptance criteria
- [ ] profiling finding recorded; the implemented fix matches the actual bottleneck *(deterministic)*
- [ ] `/v1/contradiction` returns the *same contradiction set* as compute-on-read, carrying its computed watermark *(deterministic — tested)*
- [ ] invalidation proven: a new contradiction-producing claim changes the served set (no stale cache) *(deterministic — tested)*
- [ ] hosted timing measured before/after and recorded (target: warm p95 < 5 s; cold compute at most once per instance) *(live-gated)*
- [ ] `make check` green; tier filtering + RLS untouched; no spine writes added *(deterministic)*

## Cross-cutting invariants
- Cited from `docs/tickets/00_MANIFEST.md § Cross-cutting invariants`: contradictions stay visible; append-only spine (new sqitch change only, never in-place edits); reads stay read-only; freshness is disclosed, not implied.
