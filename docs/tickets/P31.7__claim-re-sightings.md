## Goal
When a connector re-asserts an unchanged value, record that it was seen again (a `claim_evidence` link to the new
capture, with +0 claims), and make the resolver's capture-dating basis a recorded decision, so reverting values and
restated values are dated correctly.

## In scope — deliverables
1. **Re-sighting links.** Wire P31.3's `on_duplicates` hook in production (no redesign) to append a `claim_evidence`
   row linking the existing claim to the new execution's capture, under the budget rule chosen per Q5: (a) every re-sighting; (b) at most one per claim per cadence
   window; or (c) only when the capture content digest changed. **Ratified: (a) every re-sighting, uncapped** (Q5,
   2026-09-24). It stays idempotent: re-running the same capture adds +0 (one link per (claim, capture), never a
   duplicate link).
2. **Dating basis (ADR-R9-RESIGHT).** Decide whether an undated claim is dated from its earliest or its latest capture
   (or keeps the first-seen date and exposes last-seen separately). Implement the decision in the resolver and record
   the basis in `rules_fired`. Measure and accept the `input_digest` churn the change causes.
3. **Tests.** Re-ingesting an unchanged registry adds `claim_evidence` rows and +0 claims. A fixture A → B → A resolves
   to A (latest observation). Every distinct re-sighting capture adds exactly one link (no cap), and re-running the
   same capture adds +0. There is no UPDATE/DELETE.
4. **Hosted.** Deploy the new image to the scheduled jobs **by digest through P31.4's roll mechanism**
   (`sig-ops roll-jobs --image <digest> --record …`; never `:latest`; previous digests recorded for rollback). All 76
   jobs incl. batch-05 run `sha256:feff986c…` since 2026-09-25. There is **no roll onto `sig-sched-camreg-batch-05`
   until the 2026-10-10 replay's outcome is recorded** (D-P31.4-1; Q5 is already answered) — roll the other jobs
   (`--exclude sig-sched-camreg-batch-05`) and leave batch-05 on `feff986c…` until then. Every roll comes only after a bounded measurement of link volume per run
   (projected monthly rows and bytes against the provisioned disk, read live). Re-run resolution
   (`materialize.sh --apply run resolution`) as a Cloud Run job; re-run +0 on unchanged input; record the envelope delta.
5. **Growth-vs-disk measurement (operator Q5 condition).** Because every re-sighting is recorded uncapped, measure the
   real cost instead of assuming it: read-only, before and after the first rolled cadence runs, record
   `claim_evidence` row count and `pg_total_relation_size` (table + indexes), the whole-database size, and the
   Cloud SQL disk usage against the instance disk (read the provisioned size — ADR-107 records 15 GB; the operator's
   ratification cites 10 GB, so report headroom against both); derive bytes per link and a 12-month projection at the
   observed cadence mix (OSM monthly included). Record it in the run ledger and ADR-R9-RESIGHT. If the projection
   crosses a stated threshold (e.g. 50% of the disk within 12 months), the ADR's `## Revisit trigger` names that
   threshold and a follow-up (cap or digest-changed filter) is recorded as a deferral — the cap is **not** applied
   pre-emptively.

## Out of scope

- Changing volatility/half-life values (registry work, P31.8).
