# ADR-220 — Configuration generations and metadata-only promotion (P35.54)

- Date: 2026-10-23
- Status: accepted
- Ticket: P35.54 (REL-03b, on `r11/P35.54-config-generations-metadata-only-promotion`)
- Base: `r11/P35.53-release-pipeline-and-staging-origins`
- Related: SIG-REL-006 (owned here: promotion is metadata-only — latest view,
  `/releases/latest.json` and the API's current release move together, no
  release bytes copied, candidates unreachable before promotion), G3 §4.1/§4.2
  (bucket layout + envsubst route table), §4.3 (one `SIG_CONF_GEN` per
  revision; api then web), §5.1 (the promote sequence), §6.2
  (`sig.latest-pointer/2`, `sig.publication-catalog/2`), §6.3 (the
  provenance-header pair), NEW-4/NEW-7/NEW-10, RM-6 (loud absence), GT-9
  (`SIG_STAGING`), SIG-REL-002 (the promoted gate), SIG-REL-012 (class
  gates), D-P34.13-1 (branded error-page surface), P34.41 (deny maps and
  `sig.tombstone/1` bodies), P35.55 (the `withdrawn.conf` writer)

## Context

P35.53 staged releases into private namespaces and stood the release
registry + verb family. Promotion — moving the latest view onto a
candidate — must now happen by metadata alone: the immutable
`staged/{r,v,s,releases}/<pub>/` trees never move; a new immutable
`registry/conf/<gen>/` generation (promoted map, `latest.json`, the
withdrawal/selectors/labels includes, the `/releases/` index set) is
written, and `sig-api` then `sig-web` roll onto it by digest. G3 §4.2
fixes the nginx route table and the per-revision envsubst vars; §5.1 fixes
the promote sequence and its resumability. Two seams were left to this
row's judgement: how the dual-config container behaves before the dark
cutover (row 336's leg), and what "carried" means for the deny barrier
across a generation boundary.

## Decision

**D1 — envsubst at container start, dual config.** `ops/web/nginx.conf`
becomes the G3 §4.2 template verbatim (every `location`, `map` and
`include`; the carried `chrome_*`/`terms_*`/`renamed_*` glob surface
preserved under `/mnt/rel/staged/conf/` so D-P34.13-1's wiring lands
unchanged; the retired `release_*.conf` glob drops — the `X-SIG-Release`
header is env-rendered now). The stock `nginx:alpine` entrypoint runs
`/docker-entrypoint.d/*.sh` first; `40-sig-conf.sh` renders the template
plus a small `sig-headers.conf` snippet (the provenance pair + the staging
noindex line, repeated per location because an `add_header`-carrying
location inherits none from `server`) via `envsubst` on exactly
`$SIG_LATEST_PUB $SIG_LATEST_LABEL $SIG_CONF_GEN $SIG_STAGING
$SIG_ROBOTS_TAG_LINE`. Both set → render; neither → the committed legacy
config verbatim; exactly one → refuse to start (a half-set revision env is
a misconfiguration, never silently half-templated). `SIG_LATEST_LABEL`
joins the env set: `X-SIG-Release` is `"<label> <pub>"` per §4.2/§6.3 and
the label is not derivable from the pub.

**D2 — the promoted gate is a map, the latest view is a root.** `$uri_pub`
extracts the `p-<64hex>` a request names under `/r/`, `/s/`,
`/releases/`; `map $uri_pub $promoted` includes the generation's
`promoted.map` (`default 0` — unpromoted namespaces 404 by construction).
`set $sig_staging "${SIG_STAGING}"` + `set $deny_gate "${promoted}${sig_staging}"`
+ `if ($deny_gate = "00") { return 404; }` implements the §4.2/GT-9
bypass: staging never gates and carries `X-Robots-Tag: noindex`. The
latest view is `root /mnt/rel/staged/v/${SIG_LATEST_PUB}` — `/`, `/_astro/`,
`/tiles/`, `/release.json`, `/404.html` — while `/releases/`,
`/releases/index.html`, `/releases/catalog.json`, `/releases/latest.json`
`alias` into `conf/${SIG_CONF_GEN}/releases/`, and `/conf/tombstone/` stays
`internal`+`alias` so P34.41's deny-map URI shape carries verbatim.

**D3 — the generation is written whole, insert-if-absent, in one shot.**
`sig-ops release promote` composes every `registry/conf/<gen+1>/` object —
`promoted.map` (prior set + the new pub, sorted), `latest.json`
(`sig.latest-pointer/2`: label, pub, `manifest_sha256`, `activated_at`,
`conf_gen`, `class`, `approval_ref`, `previous`, `serving` digests,
`rolled_back`), `withdrawn.conf` (carried byte-identical; the empty-map
header when there is no prior generation), `selectors.conf` (carried;
the J3 §8.3 writer lands in a later row), `labels.conf` (re-composed from
the label→pub alias set — G3 line 170: "from the catalog"), and
`releases/{index.html,catalog.json,latest.json}` (generated by the release
tool alone — C4 NEW-10; `latest.json` is a byte-identical copy of the
pointer). Each object is a create-if-absent write: a second write into the
same generation refuses, and `conf/<gen>` files are never overwritten
(NEW-4/NEW-7 — every instance of a revision agrees; a generation is
immutable once served). No `staged/**` object is written or copied —
SIG-REL-006's metadata-only clause enforced by construction and asserted
byte-for-byte in the tests.

**D4 — approval checked, never created.** The verb requires `--approval`
naming a `registry/approvals/<name>.json` object of schema
`sig.promotion-approval/1` (`kind` ∈ {`standing_go`, `signed_readout`},
`class`, optional `publication_id`, `ref`, `approved_at`, optional
`expires_at`, `revoked`, `signature`). Class R requires an unrevoked,
unexpired `standing_go`; class S requires a `signed_readout` naming the
pub with a `signature` present — presence-checked only: cryptographic
verification is the operator's readout path, never the pipeline's. The
class comes from the journal's `classified` event (fail-closed `class_s`
when absent); `--class` overrides only when the journal is silent. The
approval's sha256 lands in `latest.json.approval_ref`.

**D5 — api then web by digest; prepared legs are recorded, execution is
opt-in.** `plan_service_roll` builds the `gcloud run services update` args
(digest-pinned `--image`, `--update-env-vars` carrying `SIG_CONF_GEN`,
`SIG_LATEST_PUB`, `SIG_LATEST_LABEL`, and `SIG_STAGING=0` on the public
services; `--min-instances 1` on the web leg so the latest view never
scales to zero mid-flip), refuses non-digest refs, and refuses
`SIG_STAGING=1` on any service not named `*-staging`. `apply_service_roll`
runs the update then `describe`s the service and verifies the image
digest, the env, and the ready revision — an api failure means the web
leg never starts (§4.3: never a mixed-release window). Without
`--execute-rolls` the apply writes the generation and records the roll
args `prepared` verbatim — the composed stack executes the flip by
recreating the `web` service with the new env, which is exactly what a
digest roll does per revision; the hosted leg stays the operator's (OP-24
/ row 336). A crashed promote resumes: `conf/<gen+1>` naming the same pub
skips the write and continues at the rolls; one naming another pub
refuses `generation-exists`.

**D6 — post-promote checks are invoked, never re-implemented.** The
default post-check set is structural (every generation object parses and
names this pub/gen) plus — when the store is a local directory and the
release stages an integrity manifest — `release_publish_verify`'s V7
`api_parity_check` over the staged tree, the same check `verify` ran at
stage time. A `post_checks` callable seam lets P35.56/58's V-suites
attach without the verb re-implementing them. A failed check emits a
`failed` event and refuses; success emits `promoted` carrying the gen,
label, class, approval ref, serving digests, and every roll leg's status.

## Consequences

- Promotion is a pure metadata operation: the journal + `conf/<gen+1>` +
  prepared/executed roll legs, zero `staged/**` writes — SIG-REL-006.
- Candidates are unreachable pre-promotion by the `default 0` map;
  staging's bypass is a rendered constant, never a request input — GT-9.
- The promoted gate, the latest view, and `/releases/latest.json` move in
  the same revision roll; the composed proof asserts the byte-level flip.
- `D-P35.54-1` records the one residual: a disposition logged between a
  candidate's V10 run and its promote does not reach the carried map for
  routes only the new pub serves — the P35.55 writer / V-suite owns the
  resolution (re-derivation or a re-verify gate).
- The legacy config stays a first-class fallback until row 336's cutover
  roll retires it; `ops/web/nginx-legacy.conf` is frozen verbatim.

## Revisit trigger

Revisit if the J3 §8.3 selectors writer needs per-request (not per-
revision) selector evaluation, if the approval record must carry a
verifiable signature inside the pipeline (a signed-readout verifier leg),
if the withdrawn.conf writer (P35.55) elects re-derivation over carrying —
closing `D-P35.54-1` — or when row 336's cutover retires the legacy config
path (the fallback branch and `nginx-legacy.conf` leave then).
